### Spec detail vs. code

- **Request types** (Inventory / Client / New Request; Materials consumable/non-consumable; Additional/Swap): all three equipment sources exist (`EQUIPMENT_SOURCE`), consumable materials are modeled (`is_consumable`, `linkAndDisburse`, `returnMaterial` blocks consumables from being returned), and `REQUEST_TYPE` in `constants.js` defines `ADDITIONAL`, `SWAP_REPLACEMENT`, `SWAP_RETURN`, `EMERGENCY`. Swap requests have their own queue tab (`swap_requests`) and a `swap_requests` DB table. **Done.**
- **Priority system** (Low/Medium/High/Critical + colors/sort): done — `PRIORITY_CONFIG` in `frontend/src/features/jobs/constants.js` maps each level to a label/color/icon; the Purchasing Queue's SQL and Safety's SQL both sort by severity/priority with explicit `CASE` ordering.
- **Approval decisions: Approve, Partial, Reject** — **Partial is not wired.** `ITEM_STATUS.PARTIALLY_APPROVED` is defined in `constants.js` but no service function ever sets it — `managerApproveRequest`/`managerRejectRequest` (item-level) and `workflow.service.approveJob`/`rejectJob` (job-level) are binary only. This is a real, confirmed gap against the spec, distinct from Purchasing Queue's item-*quantity* partial fulfillment (which does exist). Size: **M** (needs a manager-facing partial-approval UI + a query, not just a status flip).
- **Comments system (thread + role visibility matrix)** — **entirely missing.** No `comment`/`Comments` anywhere in `backend/src/modules/jobs` or `frontend/src/features/jobs`. Size: **L** — needs schema, thread rendering, and the visibility-matrix decision the brief already flags as unresolved for Safety (worth deciding once, for both).
- **Inspection workflow — pre-job**: extensively implemented — checklist template, draft/autosave, submit, manager sign-off (individual item decisions: `APPROVED`/`APPROVED_REPAIR`/`REJECTED`), and a genuinely nice touch: a `FLAGGED_REPAIR` result auto-creates a `Maintenance` request in the main `requests` table and flips the linked equipment to `Under_Repair`. **Done, more built out than "in progress."**
- **Inspection workflow — post-job**: not implemented. There's a `post_job_inspections` table in the schema, but nothing in `backend/src/modules/jobs` reads or writes it — it's dead. The actual inspection code (`inspection.queries.js`) writes to `job_equipment_inspections`, a third, similarly-named table. A fourth table, `job_pre_inspections`, is also present in the schema and also unused by any backend code. Three inspection-shaped tables, one of them wired. Flagging as schema drift (appendix A3), and post-job inspection specifically as **missing**. Size: **M**.
- **Permissions (who can request, by job role/status)**: `JOB_TEAM_ROLE_PERMISSIONS` exists and is checked (`canUserRequest`, `canUserApprove`) — Chief Operator/DAQ route through supervisor approval first, Engineer can't request at all. **Done.**

### Discrepancy vs. the brief's step 5 description

The brief's status table lists step 5 as "Submit draft (supervisor) → PENDING_APPROVAL / Team_Assigned." In code these are not two names for the same thing — `PENDING_APPROVAL` doesn't exist anywhere in the actual `job_status_expanded` DB enum (see A2); only `Team_Assigned` is ever written by the submit query. `PENDING_APPROVAL` exists only as a JS-side alias in `frontend/src/features/jobs/constants.js` and is handled by a case-insensitive OR check in `WorkflowActions.jsx` (`statusIs(job.status, 'PENDING_APPROVAL', 'TEAM_ASSIGNED')`). Worth confirming against the real docx which name was meant to be canonical — right now the frontend alias is dead weight the DB never produces.

### Open question 1 — visibility matrix: what the code does today

Never explicitly decided, per the brief. Here's the current, as-read state, not a recommendation:

- **List** (`GET /safety`): gated to `Super_Admin, Admin, IT_Support, Safety_Manager, Safety_Officer, Operations_Manager` at the route level (`safety.routes.js`). Anyone in that set sees **every** report, unfiltered by department or ownership — `safety.queries.js findAll` has no department/ownership WHERE clause. Non-privileged users don't hit this endpoint at all; the frontend routes them to `getMyReports` instead (own reports only, via `reporter_id = $4` filter).
- **Detail** (`GET /safety/:id`): **no role guard whatsoever** — any authenticated user, of any of the 23 roles, who has or guesses a report UUID can fetch full detail, including the non-anonymized reporter's name and department. There's no "is this your report or your department's" check anywhere in `safety.controller.getById`.
- **Status update** (`PATCH /:id/status`): gated to the same safety-admin role set at the route — but as noted above, the one UI entry point to it is additionally (and incorrectly) gated on a nonexistent `department_name` field, so it never actually renders.
- Net effect right now: **coarse role gate on the list view, no gate at all on the detail view, and a frontend role list that's already drifted from the backend's.** Nothing "department-scoped" exists in the code today — worth knowing before deciding whether department-scoping is even the intended model.

### Open question 2 — the richer incident form: sizing the delta

Confirmed against the `safety_reports` schema: **none** of the late-January spec fields exist as columns — no Immediate Actions Taken, no Impact Assessment (injury/fatality counts, property/equipment damage + ₦ cost, environmental impact, production impact enum), no Witnesses, no Attachments. The table has exactly: `reporter_id, type, severity, status, title, description, location, incident_date, is_anonymous, assigned_to, resolution, resolved_at`. `CreateSafetyReport.jsx` is a two-step type-picker + a 4-field form (date, location, severity, description) plus the two dead fields noted above.

**If the late-January form is the real target, Safety is not a 3-page module needing polish — it's a schema migration + full rebuild of the create form + a rebuild of the detail view's data model.** Sizing that separately as requested:; **L** — new migration (8+ columns across 3 conceptual groups), a multi-section form (the current single-card form doesn't have room for Impact Assessment as currently built), file upload plumbing for Attachments (nothing in the codebase currently handles safety-report file attachments), and a Detail-page redesign to show it all. This should not be scoped into the same pass as fixing the three confirmed bugs above.

**Biggest blocker to shipping Safety (current-scope, not richer-form):** the `report_type` crash on the Detail page. Nothing else matters until that's fixed — you can't reach the status-update section, the stat verification, or anything else past that point in the UI.

## Appendix — cross-cutting issues noticed (not actioned, for the later UI-consistency pass)

- **A1 — Double activity logging in Jobs equipment actions.** `equipment.controller.js`'s `disburseItem`/`startSourcing`/`itemArrived`/`returnItem` each call their own `logAction()` wrapper (`entityType`/`entityId` shape, `ACTIONS.*` constants) *and* the underlying `equipment.service.js` functions independently call `logActivity()` again internally (`resourceType`/`resourceId` shape, raw string action names like `'EQUIPMENT_DISBURSED'` vs. the controller's `ACTIONS.ITEM_DISBURSED`). Every one of these actions writes two activity-log rows with two different shapes and two different action-name strings for the same event. Not scoped to fix here, but worth a real ticket — it pollutes the audit trail this system is supposed to be reliable for.
- **A2 — Job status naming/casing drift.** `job_status_expanded` (the actual DB enum backing `jobs.status`) has 16 members, including three that look like a patch-job: `'APPROVED'`, `'POST_JOB'`, `'IN_PROGRESS'` sitting alongside the TitleCase `'Approved'`, `'Post_Job'`, `'In_Progress'` that the real workflow queries (`workflow.queries.js`) actually write. Six more enum members (`Planning, Inspection, Equipped, In_Transit, Completing, On_Hold`) are never written by any code — dead. Meanwhile `frontend/src/features/jobs/constants.js`'s `JOB_STATUS`/`JOB_STATUS_CONFIG` uses SCREAMING_SNAKE_CASE keys that don't match what's actually stored. `WorkflowActions.jsx` works around this with an explicit case-insensitive `statusIs()` helper (comment: *"Helper for case-insensitive status check"* — someone already knew) — but `JobStatusBadge.jsx` does a raw `JOB_STATUS_CONFIG[status]` lookup with no normalization, so **every job status badge in the app renders as a plain gray badge with the raw uncapitalized-mismatch string instead of its intended color/label**, because the lookup key never matches what's stored. A separate, unused `job_status` enum type (`Planned, Active, On_Hold, Completed, Cancelled`) also exists in the schema and isn't referenced by any table column — more dead schema.
- **A3 — Three inspection-shaped tables, one wired.** `job_equipment_inspections` (actually used by `inspection.queries.js`), `job_pre_inspections`, and `post_job_inspections` (both present in schema, neither referenced by any backend code). Likely an earlier design iteration left behind; worth a cleanup migration whenever schema debt gets addressed.
- **Role-array proliferation.** Beyond the Safety `SAFETY_ADMIN_ROLES` drift noted above, `jobs.service.js` and `jobs/constants.js` each define their own local `MANAGER_ROLES`/`PURCHASING_ROLES` arrays (hedging both `'Super Admin'` space-separated and `'Super_Admin'` underscore forms), separate from `frontend/src/routes/routeRoles.js`'s canonical lists and separate from the Admin-sidebar audit's findings from the prior pass. Every one of these hand-maintained role arrays is a future drift point — this is the same shape of bug as the Admin-sidebar gap found earlier, recurring inside individual feature modules.

Not investigated further (out of scope for this pass, flagging only): `E3-001` was left untouched per instruction. The 17 open SRE tasks were not reviewed, per instruction.
